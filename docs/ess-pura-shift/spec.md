# ESSプラシフト 仕様書

Googleフォームへの回答だけで、学期単位のディベートプラ／サマリープラのシフトを自動編成するシステムの仕様。

- 版: 1.0
- 想定実行基盤: Google フォーム + Google スプレッドシート + Google Apps Script

---

## 1. 目的とゴール

管理者が名簿やシフトを手作業で組む工数をゼロに近づける。理想形は次の一行に集約される。

> 全員がGoogleフォームに回答する → 管理者がボタンを1つ押す → その学期のプラが確定する

達成すべきこと:

1. メンバー情報の収集を Google フォームに一本化する
2. 参加可能コマから、条件を満たすプラ編成を自動で導出する
3. 条件を満たせない箇所を、黙って壊れるのではなく警告として可視化する
4. 一度確定したシフトは学期中固定し、毎週組み直さない

---

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| プラ | 練習活動の1単位。特定の曜日・時限に開催される |
| ディベートプラ | ディベート形式のプラ |
| サマリープラ | サマリー形式のプラ |
| コマ | 曜日 × 時限で一意に決まる時間枠。月〜土 × 1〜5限の計30コマ |
| 参加可能コマ | メンバーがそのコマに参加できると回答した枠 |
| 経験者 | 経験者または役職者。各プラに最低1人配置する対象 |
| 学期 | シフトを固定する単位（例: 2026年度後期） |
| 仮シフト | 回答収集中に随時再計算される、確定前のシフト |
| 確定シフト | 管理者が確定操作を行い、その学期の正式なシフトとして固定されたもの |
| 担当回数 | 過去の学期を含む、そのメンバーがプラを担当した累計回数 |

## 3. 全体アーキテクチャ

```
管理者
  │ ① フォーム生成（Apps Script）
  ▼
Googleフォーム ──── URL 配布 ────▶ メンバー
  │                                   │ ② 回答送信
  │◀──────────────────────────────────┘
  ▼
回答スプレッドシート
  │ ③ onFormSubmit トリガー
  ▼
ESSプラシフト（Apps Script）
  ├── メンバー名簿シートへ登録／更新
  ├── 参加可能コマの正規化
  └── 仮シフトの再計算
  │
  │ ④ 管理者が「シフトを確定」
  ▼
確定シフト（学期固定）
```

Google フォームの回答送信をトリガーに Apps Script を実行する仕組みは Google 公式にサポートされている（インストーラブルトリガー `onFormSubmit`）。フォーム自体も Apps Script の `FormApp` から生成できるため、①〜④はすべてスクリプト内で完結する。

## 4. データモデル

### 4.1 コマ (Slot)

- 曜日: 月・火・水・木・金・土 の6種
- 時限: 1〜5限 の5種
- コマ総数: 30
- コマID: `<曜日インデックス0-5>-<時限1-5>`（例: 月2限 = `0-2`）

### 4.2 メンバー (Member)

| 項目 | 型 | 必須 | 備考 |
| --- | --- | --- | --- |
| memberId | string | ○ | システム採番。氏名の正規化キーで名寄せ |
| name | string | ○ | 氏名 |
| gender | enum | ○ | `male` / `female` / `other`。`other` は男女比計算の対象外として扱い、人数条件のみに算入する |
| isVeteran | boolean | ○ | 経験者・役職者フラグ |
| availableSlots | SlotID[] | ○ | 参加可能コマ。0件の回答も許容し、警告対象とする |
| unavailableNote | string | | 参加できない日などの自由記述 |
| pastAssignmentCount | number | ○ | 過去の担当回数。初期値0 |
| submittedAt | datetime | ○ | 回答日時 |

同一人物が複数回回答した場合は、**最新の回答で上書き**する（`submittedAt` の降順で1件を採用）。

### 4.3 プラ (Pura)

| 項目 | 型 | 備考 |
| --- | --- | --- |
| puraId | string | 学期内で一意 |
| type | enum | `debate` / `summary` |
| slotId | SlotID | 開催コマ |
| memberIds | string[] | 配置メンバー |

### 4.4 学期シフト (SemesterShift)

| 項目 | 型 | 備考 |
| --- | --- | --- |
| semesterId | string | 例: `2026-fall` |
| label | string | 例: `2026年度後期` |
| status | enum | `draft`（仮） / `confirmed`（確定） |
| puras | Pura[] | |
| warnings | Warning[] | |
| generatedAt | datetime | |
| confirmedAt | datetime | 確定時のみ |

## 5. Googleフォーム仕様

Apps Script から自動生成する。設問構成:

| # | 設問 | 形式 | 必須 |
| --- | --- | --- | --- |
| 1 | 氏名 | 記述式 | ○ |
| 2 | 性別 | ラジオ（男性／女性／回答しない） | ○ |
| 3 | 経験者・役職者ですか | ラジオ（はい／いいえ） | ○ |
| 4 | 月曜に参加できる時限 | チェックボックス（1〜5限） | |
| 5 | 火曜に参加できる時限 | チェックボックス（1〜5限） | |
| … | 水〜土も同様 | チェックボックス（1〜5限） | |
| 10 | 参加できない日・備考 | 段落 | |

曜日ごとに設問を分けることで、30個のチェックボックスを1問に詰め込むより回答負荷を下げる。回答は `availableSlots` に正規化して名簿シートへ書き込む。

## 6. 編成ルール

制約はハード（必ず守る／破るなら配置しない）とソフト（できるだけ守る／破ったら警告）に分ける。

### 6.1 ハード制約

| ID | 内容 |
| --- | --- |
| H1 | メンバーは自分の参加可能コマにしか配置されない |
| H2 | 同一コマに同一メンバーを重複配置しない（ディベートとサマリーの掛け持ち不可） |
| H3 | 1人あたりディベートプラは最大1回、サマリープラは最大1回 |

H2 は「月曜3限のディベートプラとサマリープラに同じAさん」というケースを機械的に排除する。同じ時間に2つの活動へ参加することは物理的に不可能なため、これは調整対象ではなく禁止事項として扱う。

### 6.2 ソフト制約

| ID | 内容 | 違反時 |
| --- | --- | --- |
| S1 | 1プラの人数は4〜6人 | 4人未満=不足、7人以上=超過 として警告 |
| S2 | 各プラに経験者・役職者を最低1人 | 経験者0人として警告 |
| S3 | 各プラの男女比をできる限り均等に | 偏りとして警告 |
| S4 | 1人につきディベート1回・サマリー1回 | 1活動のみとして自動処理し、情報として記録 |
| S5 | 過去の担当回数が少ない人を優先 | 偏りとして記録 |

S4 は「両方に入れないなら1活動のみで確定させる」という**縮退動作**であり、エラーではない。空きコマの都合で2活動に入れないメンバーが出るのは正常な結果として扱う。

### 6.3 評価関数

局所探索での比較に用いるスコア。値が小さいほど良い（ペナルティの総和）。

```
score = w1 * Σ(人数逸脱)          // 4未満なら (4 - n)^2、7以上なら (n - 6)^2
      + w2 * Σ(経験者不足)        // 経験者0人のプラ1つにつき 1
      + w3 * Σ(男女比の偏り)      // |男性数 - 女性数| （other は除外）
      + w4 * (2活動に入れない人数)
      + w5 * (担当回数の分散)      // 今学期後の累計担当回数の分散
```

推奨する重み: `w1=3, w2=5, w3=1, w4=2, w5=1`。

経験者不足の重みを最大にするのは、「初心者だけの班」がプラとして成立しないため。男女比は他条件と競合したときに最初に譲る位置づけで、完全な同数が不可能な場合は他条件を優先し、その中で最もバランスの良い組み合わせを選ぶ。

## 7. 編成アルゴリズム

### 手順1: 開催コマの決定

1. 各コマについて参加可能メンバー数を集計する
2. 参加可能者が4人未満のコマは開催候補から除外する
3. 必要プラ数を見積もる
   - ディベートプラ数 = `ceil(全メンバー数 / 5)`
   - サマリープラ数 = `ceil(全メンバー数 / 5)`
   - 1プラあたり5人（4〜6人の中央値）を基準とする
4. 参加可能者数の多いコマから順に、必要数だけコマを選ぶ。ディベートとサマリーは可能な限り別コマに割り当て、同一コマに両方を置く場合は H2 の掛け持ち禁止が効くことを前提に配置する

### 手順2: 初期割当（貪欲法）

配置順は **選択肢の少ない人を先に** 決める（most-constrained-first）。同点は担当回数の少ない順。

```
候補メンバーを次のキーで昇順ソート:
  1. 配置可能なプラ数（参加可能コマと開催コマの積集合の大きさ）
  2. pastAssignmentCount
  3. 氏名（安定ソートのため）

各メンバーについて:
  ディベートプラの中から、H1・H2・H3 を満たし
  かつ score の増分が最小となるプラへ配置
  同様にサマリープラへも配置
  配置先が無ければ「1活動のみ」または「未配置」として記録
```

### 手順3: 経験者の充足

経験者0人のプラが残っている場合、経験者を複数抱えるプラから移動できないか探す。

```
経験者0人のプラ P について:
  経験者2人以上を持つプラ Q を探す
  Q の経験者 v が P のコマに参加可能で、H2・H3 を破らないなら v を P へ移す
  移動できる経験者がいなければ、非経験者との交換（swap）を試みる
```

### 手順4: 局所改善

`score` が改善しなくなるまで、または上限回数（推奨2000回）に達するまで次を反復する。

- **move**: メンバー1人を別のプラへ移す
- **swap**: 異なる2つのプラのメンバーを入れ替える

いずれもハード制約を破る操作は候補にしない。改善が得られた操作のみ採用する（山登り法）。局所解を抜けるため、乱数シードを変えて数回実行し、最良解を採用してもよい。

### 手順5: 検証と警告生成

完成した編成に対して第8章の警告を全件走査し、`warnings` に格納する。

## 8. 警告仕様

| コード | 重大度 | 条件 | 表示例 |
| --- | --- | --- | --- |
| `SHORTAGE` | 警告 | プラの人数が4人未満 | ⚠ 月曜2限 ディベートプラ: 3人（人数不足） |
| `OVERFLOW` | 警告 | プラの人数が7人以上 | ⚠ 水曜4限 サマリープラ: 8人（人数超過） |
| `NO_VETERAN` | 重大 | プラに経験者・役職者が0人 | ⚠ 木曜1限 ディベートプラ: 経験者0人 |
| `GENDER_IMBALANCE` | 情報 | 男女差が3人以上 | ⚠ 金曜3限 サマリープラ: 男性5人・女性1人 |
| `SLOT_UNDERSTAFFED` | 警告 | 開催候補コマの参加可能者が4人未満 | ⚠ 土曜5限: 参加可能者2人 |
| `SINGLE_ACTIVITY` | 情報 | 2活動に配置できなかったメンバー | ⚠ Aさん: 空きコマの都合で1活動のみ |
| `UNASSIGNED` | 重大 | どのプラにも配置できなかったメンバー | ⚠ Bさん: 配置可能なコマがありません |
| `NO_RESPONSE` | 警告 | 名簿にいるが未回答のメンバー | ⚠ Cさん: フォーム未回答 |

重大度が `重大` の警告が残っている状態でも確定操作は可能とするが、確定前に確認ダイアログで件数を提示する。

## 9. 仮シフトと確定シフト

### 状態遷移

```
（なし）
  │ 学期を作成
  ▼
draft（仮シフト）───── 回答が届くたびに再計算 ─────┐
  │                                                │
  │ 管理者が「シフトを確定」                        └──▶ draft
  ▼
confirmed（確定シフト）
  │
  │ 管理者が「確定を解除」（要確認）
  ▼
draft
```

- `draft` の間は、フォーム回答が届くたびに全体を再計算してよい。前回結果との継続性は保証しない
- `confirmed` になった時点で編成は固定される。以降に回答が届いても**自動再計算はしない**。新しい回答は名簿にのみ反映し、「確定後に届いた回答があります」と管理者へ通知する
- 確定時に、配置された各メンバーの `pastAssignmentCount` へ今学期の担当回数を加算する。これが次学期の公平化（S5）の入力になる
- 確定解除した場合は加算を取り消す（べき等性のため、加算履歴を学期IDとともに記録しておく）

学期中はこの確定シフトが固定的に運用される。

```
月曜2限 → ディベートプラ
月曜3限 → サマリープラ
水曜4限 → ディベートプラ
```

## 10. 管理者の操作

スプレッドシートのカスタムメニュー「ESSプラシフト」から実行する。

| メニュー | 動作 |
| --- | --- |
| フォームを作成 | 第5章の構成でフォームを生成し、回答先を本スプレッドシートに設定、`onFormSubmit` トリガーを登録してURLを表示 |
| 学期を作成 | `semesterId` と `label` を入力し、`draft` の学期を作る |
| 仮シフトを再計算 | 現在の名簿で編成アルゴリズムを実行し、結果と警告を出力 |
| シフトを確定 | 警告件数を確認のうえ `confirmed` へ遷移、担当回数を加算 |
| 確定を解除 | `draft` へ戻し、担当回数の加算を取り消す |
| 名簿を表示 | 回答状況と未回答者の一覧を表示 |

## 11. シート構成

| シート名 | 役割 |
| --- | --- |
| `フォーム回答` | フォームが自動生成する生の回答。編集しない |
| `名簿` | 正規化済みメンバー情報。`pastAssignmentCount` を保持 |
| `シフト` | 学期ごとの編成結果。曜日 × 時限のマトリクス表示 |
| `警告` | 生成された警告の一覧 |
| `設定` | 現在の学期ID、人数の上下限、評価関数の重みなど |

人数の上下限（既定 4／6）と重みは `設定` シートで変更できるようにし、コードにハードコードしない。

## 12. 非機能要件・制約

- **実行時間**: Apps Script の実行時間上限は6分。メンバー100人・30コマ規模で局所探索2000回が上限内に収まることを前提とする。超える場合は反復回数を `設定` で下げる
- **冪等性**: 同じ名簿・同じ乱数シードで再計算した場合、同じ編成が得られること
- **氏名の名寄せ**: 前後の空白除去と全角半角スペースの統一のみ行う。同姓同名は自動では区別できないため、警告として管理者に提示する
- **権限**: フォーム・スプレッドシート・トリガーの作成権限を持つGoogleアカウントで実行する

## 13. 未確定事項

実装前に決める必要がある項目。

1. ディベートプラとサマリープラの開催数は等しくてよいか、比率を変えるか
2. 経験者が総数に対して不足している場合（経験者数 < プラ総数）の扱い。プラ数を減らすか、経験者0人のプラを許容するか
3. 性別「回答しない」を選んだメンバーの男女比上の扱い（本仕様では計算対象外としている）
4. 学期をまたぐ担当回数のリセット方針（年度で0に戻すか、累計を持ち続けるか）
5. 確定シフトを学期途中で部分修正する運用（1コマだけ差し替えたい場合）の要否
